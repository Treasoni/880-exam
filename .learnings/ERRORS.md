### 核验判据失真族（4 次）：判据与被检内容共用字符集，或未断言解析规模

**错误**：三次都是**核验脚本自身失真、却报绿**，结论差点从错误的中间输出得出——
1. `git diff … | grep -v "^[+-][+-]"` 想滤文件头，把 `-- [ ] 错` / `+- [x] 错` 这类真实变更行一起吞掉（变更行 = 标记 + 原文，原文首字符可能就是 `-`/`+`），一度误判「判分卡 diff 为空」；改用未过滤的原始 `git diff` 才看到三处勾选。
2. `git diff | grep -c "No newline at end of file"` 未锚定行首，而 `RULES.md` / `ERRORS.md` 正文里就写着这个字面串——经验库一改计数必然红灯，判据**永久假阳性**（实测 10 条里真实 0 条）。
3. 答案卷切块核验脚本把章节号当题号透传，22 块只切出 2 块，却照样打印「切块数一致 / 内容不同的题号：[]」——差点把「没切对」读成「答案卷无改动」（上游 `KeyError` 兜住了，但假绿行已先输出）。
4. `json.dumps` 写回聚合 JSON 未补末尾换行，制造 `-}`/`+}` 的 `No newline at end of file` 假 diff；而当时的 round-trip 自检**把源文件记成了「无末尾换行」**——自检脚本与写回脚本互相印证同一个错误前提，两边都绿。判据的前提本身就是错的。

**触发场景**：把「字面串计数」或「两版比对结果为空」当自检判据；且被检内容本身可能含该字面串，或分组解析可能整体失败（正则漂移、键传递写错）。

**根因**：判据与被检对象**共用字符集**（1、2），或判据的**前提未被断言**（3 解析规模、4 源文件格式）——两种情况都会让失真表现为「绿灯」。这与项目里已有的一条同族教训一致：过滤器/断言不能与被检内容同源。

**修复**：
- 判据锚定：`grep -c '^\ No newline at end of file'`（行首锚定）+ 一律 `git diff -- <本次文件>` 收窄范围；够不上锚定就换结构化判定。
- 机制三层（本次新增，覆盖第 3 类）：
  1. **源头校验**：`lib880.split_answer_sheet` / `answer_sheet_key_errors` 成为答案卷分块的**单一判据**，锚定 `papers.json` 的 `paper_no` 期望集合；
  2. **陈旧检测**：`lint_content.py` 对**全部**答案卷跑该判据（不止新写入的），缺块 / 多块 / 题号错位立即报错退出 1；
  3. **流程步骤**：`RULES.md` 写明核验脚本必须锚定期望集合、且新判据要喂负样本。
- 验证：正样本 7 张答案卷全绿；负样本（截掉第 6 题）函数级报 `答案卷缺少题块: 一6`，端到端 lint 退出码 1；清理后复跑全绿。

**预防措施**：
- 写任何 `grep` 型判据前先自问「我数的那串字符，会不会出现在被数的文本里」；用 `grep -v` 裁 diff 前先自问「被裁的行会不会以同样字符开头」。
- 核验脚本先**断言解析规模**（切出 22 块 / 618 条）与期望集合相等，再报差异；「无差异」在分组出错时没有任何信息量。
- 结论只从未过滤的原始输出得出，过滤器仅用于展示。

### 核验前提未核实族（3 次）：查错对象 / 用错工具契约 / 拿转述当事实

**错误**：本次替换卷子-04 第 8 题解析，核验环节三次给出「格式正确、语气笃定」的错误信号——
1. **查错对象**：取事实源条目时凭对第 6 题的印象硬编码 qid `gs-c04-comprehensive-choice-003`，取回一道**多元函数**题（答案 C）。因为答案对不上，一度准备按「`papers.json` 与答案卷不一致」立案。把卷子-04 的 22 题映射整表打印出来才对上：第 8 题是 `gs-c02-comprehensive-choice-014`（答案 B），与判分卡一致，根本不存在不一致。
2. **用错工具契约**：探针写 `q["text"] in block` 判「题干在块内」，22 块全是 False。真相是 `lib880.split_answer_sheet` **故意跳过** `**N.** …` 题干行（块从题干下一行开始）——是探针不符合工具契约，不是文件有缺陷。
3. **拿转述当事实**：收尾前准备向用户报告「判分卡已勾 `半会`，与 `attempts.json` 记录的 `对` 冲突」。实查 `attempts.json` 里 `paper_id=paper-04` 的记录 **0 条**、卷子 `status: created`——paper-04 从未判分，判分卡上那 10 处是用户手填待判的勾选，冲突不存在。那个「对」来自上文摘要的一句转述，我拿它当了事实。

**触发场景**：任何「先取数据、再拿数据下结论」的核验（取条目、探结构、报冲突）。第 1、2 类发生在换新题号 / 换新工具时；第 3 类在长会话被压缩后尤其容易——摘要里的转述读起来就像刚读到的事实。

**根因**：三次的失效点都不在被检内容，而在**核验的输入前提**——对象（1）、工具语义（2）、事实来源（3），三处前提一处都没被断言。前提错了，输出照样格式正确、语气笃定，还会把「我的探针坏了」伪装成「文件坏了」。

这与同日的「核验判据失真族」是同一 meta-族的两面：那一族错在**判据**，这一族错在**前提**。

**修复**：
- 取事实源条目一律**从卷面反查**：读 `papers.json` 的 `paper_no → qid` 映射拿 id，禁止凭记忆硬编码题号。
- 用 `lib880` 解析函数前先按其**真实契约**写探针（`split_answer_sheet` 的块不含题干行）；探针报异常先怀疑探针，回读函数源码确认，不直接立案查文件缺陷。
- 断言「A 与 B 冲突」前必须**读 B 的盘面值**（该 paper 有几条记录、`status` 是什么）；转述、摘要、上一轮结论都不算事实。

**预防措施**：
- 「取数据 → 下结论」之间的每条输入前提，先写一行断言（对象对不对 / 契约是什么 / 来源是哪份文件），断言不过不进下一步。
- 长会话压缩后，摘要里的任何**具体值**（判分、状态、计数）使用前重新读盘核对。
