## 2026-09-15（09-24 补记第 4 次复发）

### 核验前提未核实族（4 次）：查错对象 / 用错工具契约 / 拿转述当事实

**错误**：本次替换卷子-04 第 8 题解析，核验环节三次给出「格式正确、语气笃定」的错误信号——
1. **查错对象**：取事实源条目时凭对第 6 题的印象硬编码 qid `gs-c04-comprehensive-choice-003`，取回一道**多元函数**题（答案 C）。因为答案对不上，一度准备按「`papers.json` 与答案卷不一致」立案。把卷子-04 的 22 题映射整表打印出来才对上：第 8 题是 `gs-c02-comprehensive-choice-014`（答案 B），与判分卡一致，根本不存在不一致。
2. **用错工具契约**：探针写 `q["text"] in block` 判「题干在块内」，22 块全是 False。真相是 `lib880.split_answer_sheet` **故意跳过** `**N.** …` 题干行（块从题干下一行开始）——是探针不符合工具契约，不是文件有缺陷。
3. **拿转述当事实**：收尾前准备向用户报告「判分卡已勾 `半会`，与 `attempts.json` 记录的 `对` 冲突」。实查 `attempts.json` 里 `paper_id=paper-04` 的记录 **0 条**、卷子 `status: created`——paper-04 从未判分，判分卡上那 10 处是用户手填待判的勾选，冲突不存在。那个「对」来自上文摘要的一句转述，我拿它当了事实。
4. **隔离作用域（2026-09-24 复发）**：为「`--rebuild` 保留勾选」写回归测试时，`patch.multiple` 只挂了读路径与部分写路径（漏了 `SOLUTION_OVERRIDES_PATH`），最后两步 `--rebuild-answers` 实际**跑在真实 vault 上**——只因「内容未变不写盘」才没落笔；断言 `updated: 2026-09-24` 失败（读到的是真答案卷）才暴露。失效点还是前提：测试文件头写着「所有写入都限制在临时目录」，没人断言过。

**触发场景**：任何「先取数据、再拿数据下结论」的核验（取条目、探结构、报冲突、给测试划隔离范围）。第 1、2 类发生在换新题号 / 换新工具时；第 3 类在长会话被压缩后尤其容易——摘要里的转述读起来就像刚读到的事实；第 4 类在写隔离型测试时——补丁按「脑子里那份清单」列，漏项无声。

**根因**：四次的失效点都不在被检内容，而在**核验的输入前提**——对象（1）、工具语义（2）、事实来源（3）、隔离范围（4），每处前提都没被断言。前提错了，输出照样格式正确、语气笃定，还会把「我的探针坏了」伪装成「文件坏了」。

这与同日的「核验判据失真族」是同一 meta-族的两面：那一族错在**判据**，这一族错在**前提**。

**修复**：
- 取事实源条目一律**从卷面反查**：读 `papers.json` 的 `paper_no → qid` 映射拿 id，禁止凭记忆硬编码题号。
- 用 `lib880` 解析函数前先按其**真实契约**写探针（`split_answer_sheet` 的块不含题干行）；探针报异常先怀疑探针，回读函数源码确认，不直接立案查文件缺陷。
- 断言「A 与 B 冲突」前必须**读 B 的盘面值**（该 paper 有几条记录、`status` 是什么）；转述、摘要、上一轮结论都不算事实。
- 测试隔离（第 4 类的机制）：`patch.multiple(lib880, …)` 必须覆盖本次流程**会写到的每个路径**，并在跑主流程前断言一遍——判据与写法见 `RULES.md`「测试补丁要覆盖全部写盘目标」。**未落实**：尚无代码级守卫（`tests/` 里的隔离声明仍是人工维护的清单），加守卫前不要假定测试碰不到真实 vault。

**预防措施**：
- 「取数据 → 下结论」之间的每条输入前提，先写一行断言（对象对不对 / 契约是什么 / 来源是哪份文件 / 隔离范围够不够），断言不过不进下一步。
- 长会话压缩后，摘要里的任何**具体值**（判分、状态、计数）使用前重新读盘核对。
- 测试报错先怀疑**测试自己**：本次断言失败读到的 `updated: 2026-09-24` 来自真实 vault，先查作用域再查被测代码。

## 2026-10-11

### 写盘前提未体检族（3 次）：并发会话竞写 / 渲染结论未实测 / lint 判据近似

**错误**：修 paper-06「渲染失败了」时，三处输出「动作完成、看着自洽、其实错」：
1. **并发会话竞写**：本会话压缩重启后带着「未修改任何项目文件」的旧摘要，直接开改 `scripts/lib880.py`；同库另一个会话（`880-exam-b9`，11 分钟前启动、正在做同一件事）已在改同一批文件。Edit 工具报「file modified on disk since you last read it」才暴露。我加进去的 `RELATIVE_IMAGE_RE` / `INLINE_DOLLAR_PAIR_RE` / `HTML_TAG_START_RE` 与 peer 实现重叠，其中 `HTML_TAG_START_RE` 落地即死代码。**证据一直摆在手边没用**：动手前 `git status` 就会显示 `M scripts/lib880.py`，而那个改动根本不是我做的；`ListAgents` 也一直列着 busy 的 peer。此后两个会话在同一批文件上重叠写了一段，靠 SendMessage 按文件切才止住。
2. **渲染结论未在 vault 实测**：我在 `lib880.py` 注释里把「公式区外的裸 `<` 转义成 HTML 实体 `&lt;`」当成正解。peer 在 vault 里做最小复现实测：Live Preview **不解码实体**——`A. M&lt;N&lt;P` 的正文里仍是字面 `&lt;`，而 `A. M\<N\<P` 正常渲成 `M<N<P` 且后续内容不再裸露。我的方案是从原理推的，没做最小复现就写进了共享文件。
3. **lint 判据用近似条件代替渲染层本体**：`inline_dollar_lines` 我写成「非独立块的行只要含 `$$` 即残留」，把**合法的整行公式** `$$x=1$$` 判成错误——命中的不只有 paper-04 答案卷，还有**用户在判分卡-05 尾部手写的「解答题第 6 题详解」里的三行整行公式**。渲染层实际只降级「同行另有正文」的 `$$…$$`。按这条误报去「修」，等于改坏用户手写的排版。

**触发场景**：①同一 vault 被两个会话同时处理同一请求（用户开两个窗口 / 压缩后旧会话仍在跑）；②把「Obsidian 会怎么渲染」写成规则、生成器或判据之前；③为渲染层归一写产物侧 lint 判据时。

**根因**：三次失效点都不在被改内容，而在**动手前的前提**：谁在写（1）、渲染真实行为是什么（2）、判据是不是渲染层本体（3）。与 09-15「核验前提未核实族」同源——那条是**读**数据前不核实前提，这条是**写**文件前不核实前提。共同点：前提错了，动作照样完成、输出照样自洽，错误只在另一个会话 / 另一个视图 / 另一条判据里现形。

**修复**：
- 判据改对：`inline_dollar_lines` 改为**以渲染层本体为 oracle**（逐行 `lib880.normalize_math_delimiters(line) != line` 才算残留，正则只作预筛）；判据本体仍在 `lib880`（`INLINE_DOLLAR_PAIR_RE` / `RELATIVE_IMAGE_RE`）单一出处之内。`bare_angle_lines` 一开始就用 oracle 写法，无此问题。
- 实测落地：`\<` 生效、`&lt;` 不生效，规则文档 `obsidian-content.md` 与 `lib880` 注释统一为 `\<` 并写明「不能改用 HTML 实体」及原因。
- 分工止血：与 peer 约定按文件切（它 `lib880.py`/`make_paper.py`/`wrong_book.py` + 全库重刷，我 `lint_content.py`/`tests`/规则文档/工作流记录/复核），此后无竞写。
- **未落实**：没有机制能阻止两个会话同时开工——工作流状态文件只有一个 `current_phase`，表达不了「谁在写哪些文件」。当前靠规则自觉执行。

**预防措施**：
- **动手前先体检**：写盘或跑命令前先 `git status --porcelain` + `ListAgents`。`git status` 里出现**不是自己做的**改动、或 `ListAgents` 有 busy 的同库 peer → 先 SendMessage 分工，不写。
- **「file modified on disk」是硬停信号**：Edit 报这句就停手，重读文件 + 查 peer，禁止按旧上下文继续打补丁。压缩摘要里的任何状态（「尚未修改任何文件」）动手前一律重新读盘核对。
- **渲染行为先在 vault 实测**：任何「Obsidian 会怎么渲 X」的结论，先做最小复现文件在实时预览里实测（`dev:dom` 读正文 / 截图），再写进规则、生成器或判据。原理推导、别处经验、摘要转述都不算。
- **产线判据以渲染层为 oracle**：产物侧 lint 判据写 `render(text) != text`，正则只作预筛；禁止手写近似条件——近似会把合法写法判成错，还会诱导去改用户手写内容。

## 2026-10-11（本会话续记）

### 工具契约按子命令/API 分叉族（4 次）：`screenshot` 的 path / `--all` 的作用域 / `getMode` 的粒度 / 自动提交的中间态

**错误**：接着修 880 渲染缺陷时，四处「按字面含义用工具、动作完成、结论错」：
1. **`dev:screenshot path=` 是输出路径，被我当成输入笔记路径**：我想截一张临时笔记，写了 `obsidian dev:screenshot path=workspace/tmp-callout-math.md`——它把**截图 PNG 覆盖写进了那篇笔记**。随后 `open` 该文件看到二进制乱码，我一度当成「渲染出乱码」，白跑一轮才想到是自己写坏了文件。（同一 CLI 里 `open path=` 是**输入**文件、`dev:screenshot path=` 是**输出**文件，`path` 这个标记名不代表同一件事。）
2. **`wrong_book.py --all` 在写入模式下只重刷默认科目**：`--all` 只在 `--check` / `--due` 分支展开成两科，写入路径仍用单数 `subject`。我先跑了 `--all`，看到「已更新错题本：错题本.md」就准备宣布「全库重刷完毕」；实际 `线代错题本.md` 停在 10:02（早于本轮 `lib880` 改动），是 `lint_content.py` + `--check --all` 报红才暴露——差点把陈旧产物当已重刷交付。
3. **`view.getMode() === "source"` 不能区分「源码模式」与「实时预览」**：我拿它当「正在实时预览」的凭据去截图，那张图整屏是原始 Markdown（`$$`、`> [!info]` 全裸露）。差一点按「渲染失败」立案；实际那个 leaf 处在 Source 模式，用 `view.setState({mode:"source", source:false})` 强制实时预览后，同一区域渲染完全正常。
4. **自动提交把盘面上的临时破坏态提交进了 HEAD**：我为验证新回归测试会红，把 `wrong_book.py` 的写入目标临时改回旧行为（留了 `# TEMP-OLD-BEHAVIOUR` 标记），跑完再改回来。这个 vault 装了自动备份（每秒级 `vault backup:` 提交），中途快照把带标记的版本提交了——`git diff` 里出现 `-targets = [subject]  # TEMP-OLD-BEHAVIOUR`，即 HEAD 曾是半成品。

**触发场景**：①用 CLI 子命令但只看标记名不看语义；②复用 `--all` / `--subject` 这类「作用域开关」时；③拿一个**更粗**的状态字段（`getMode`）当**更细**事实（源码模式 vs 实时预览）的判据；④在**会自动提交**的仓库里，把「故意改坏再改回」的验证手法落在工作区文件上。

**根因**：四次都是**拿标记/字段的字面含义替代了它的真实契约或真实状态**。与 09-15「用错工具契约」（`split_answer_sheet` 的块不含题干行）同源，是那一类的**复发**——`RULES` 里那条只写了「用 `lib880` 库函数前先读契约」，没覆盖 **CLI 子命令**、**CLI 作用域开关**、**Obsidian API**，也没覆盖「一个字段的粒度够不够」。第 4 次是另一个面：把「工作区 = 我的草稿纸」当默认，忘了它同时是自动提交的事实源。

**修复**：
- **已修源码（`--all` 作用域）**：`wrong_book.py` 写入/`--list-states` 路径改为遍历 `targets = 两科 if args.all else [subject]`，与 `--check` / `--due` 语义对齐；新增回归测试 `test_all_regenerates_both_subjects_but_subject_stays_scoped`（先 `--all` 断言两科文件都在，再删高数本跑 `--subject linear-algebra` 断言不回写高数本）。**已喂负样本**：临时把写入目标改回单科，该测试如预期红在「--all 必须覆盖两科」。
- **已修源码（同族输出点遗漏）**：`wrong_book.py` 的**待复习**条目题干仍写 `{q['text']}` 原文（**已掌握归档**路径早已走 `prepare_stem_text(effective_text(...))`）——即同类文本的两条渲染路径口径不一，且待复习条目的 `text-overrides` 覆盖被静默忽略。已改为与归档路径同一层。当前产物无变化（15 条待复习里没有题干会被归一改动的题），属**潜在**缺陷；量过了：全库 618+311 题里 36 题题干会被归一改动，其中 4 题在错题本内、全在已掌握归档（那条路径本就归了）。
- **未落实**：`dev:screenshot` / `open` 的输入输出契约没有写进任何规则文件，仍靠自觉；「验证渲染」也没有固化成默认动作（见 RULES 新增条）。

**预防措施**：
- **CLI 用法先看语义不看标记名**：同一 `path=` 在不同子命令下可能是输入或输出。写盘类参数（输出文件）尤其要确认——写错会**覆盖**输入。投影/截图类命令，先把「哪个参数是产物」说清楚再执行。
- **作用域开关要核对每个分支**：`--all` / `--subject` / `--days` 这类开关，`grep` 出它在代码里的**每一处**使用分支，确认语义一致；只看它在一个分支（`--check`）的行为就推广到全部是错的。
- **细粒度问题用细粒度字段**：判断「Obsidian 是否在实时预览」必须落到 `setState({mode:"source", source:false})` 这类**显式设定**，不能用 `getMode()==="source"` 反推。缺省值/枚举粒度不够时，先显式设定再断言。
- **自动提交的仓库别留破坏态**：本 vault 有秒级自动备份；凡「故意改坏→验证→改回」的操作，改坏的对象要么换成**工作区外的临时副本**，要么先确认能在一个提交周期内改回。验证回归测试是否变红，优先用**独立的临时改动分支/副本**，不要落在会被提交的源码上。
- **给一类文本加归一化时，grep 出同族全部输出点**：改渲染层归一时，`grep` 该文本字段（如 `q['text']` / `q["solution"]`）的所有拼接位置，一次改全；只改被点名那一处，另一条路径就会留下同源缺陷（本次待复习题干即如此）。
