### 基础设施模板的修复要用该工具真实跑一遍流程才算验证

**类别**：best_practice
**优先级**：high
**状态**：pending
**范围**：`.claude/workflows` / `.claude/scripts` 维护

**摘要**：改状态机模板/配置这类「工具读的输入」时，改完读一遍觉得对不算验证——要用被改的工具**真的驱动一遍**（本轮的 `complete P3 → start P4 → complete P4` 端到端跑通、末态与盘面一致），并且给新加的检查脚本喂**负样本**（带 `— 拼卷` 后缀的阶段行）确认它真能报错，否则检查脚本绿灯可能只是「没查」。

**详情**：
- 事实：本轮修 880-exam 状态模板（阶段行 token 必须落到行尾 + 补 `## 异常记录`）后，用真实 `todo-state.sh` 流程把 P3/P4 收尾走通；新脚本 `check-workflow-state.sh` 用构造的坏行实测报出精确到行的错误，三个真实文件全绿。
- 根因：模板缺陷的失败方式往往是**静默**的（frontmatter 被提前置 `done`、行尾正则匹配不到），读代码很容易看漏；只有跑一遍才暴露。

**下次做法**：涉及工具输入格式的修复，验收标准写成「用该工具跑通一次 + 检查脚本对负样本报错」，两条都过才归档记录。

### 聚合事实源的改动核验：按「条目 × 字段」结构化比对，不看行 diff

**类别**：best_practice
**优先级**：high
**状态**：pending
**范围**：`workspace/question-index.json` 等聚合事实源 / `scripts` 维护

**摘要**：`question-index.json` 是缩进 2 的聚合 JSON，行 diff 会把「一条 `solution` 变长」放大成几十行错位噪声，而且基线是 HEAD、混带别人未提交的改动；要证明「这次只改了该改的」，得写一次性脚本按 `id` 逐条比对每个字段，确认**变更条目集合**与**每条变更字段集合**两个集合都与本次意图对应，而不是数 `git diff --stat` 的行数。

**详情**：
- 事实：本次替换 1 条题的解析后，`git diff` 显示约 22 条题的 `solution` 都「变了」——实际只有 `gs-c05-comprehensive-choice-005` 是我改的，其余 21 条是上一会话遗留的未提交改动（字面 `\n` 解码）。结构化比对给出每条 `fields=['solution']`，证明无结构损伤、只有 `solution` 一个字段变动。
- 根因：pretty-print 的 JSON 里任何一处长度变化都会让后续所有行位错位，行级 diff 对聚合事实源基本没有可读性；且 HEAD 基线会把历史欠账算到本次头上。
- 附带收获：写回这类人工维护的 JSON 前，先做一次 round-trip（读入 → 原样 `json.dumps(ensure_ascii=False, indent=2)` → 与源文件比对），确认序列化参数与源一致（含**无末尾换行**），否则自己的写入会额外制造一份全文件 diff，把真正的改动淹掉。

**下次做法**：改聚合事实源后，核验脚本固定输出两个集合——`changed_ids` 与每条 `changed_fields`；两者逐一对应上本次意图，再谈 `lint_content.py`。写入前先跑 round-trip 比对确认零差异。
